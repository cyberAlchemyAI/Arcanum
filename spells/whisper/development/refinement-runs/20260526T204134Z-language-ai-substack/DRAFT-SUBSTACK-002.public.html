The First Thing a Tool Needs Is a Name

A draft essay on language, generative AI, and the strange new possibility of creating small operational tools out of words.

Transport: Substack research post For: AI-curious creative builders Status: reading draft

Naming

You know the moment when a messy workflow becomes easier because someone finally gives it a name? The work itself has not changed yet. The tabs are still open, the notes are still scattered, the next step is still half felt. But the moment the pattern gets named, it stops being fog. It becomes something you can point at, return to, improve, and share.

That small act is easy to underestimate because language feels ordinary. We use words all day, so we forget that a word can be more than a label. A word can hold a behavior in place. A phrase can compress a method. A schema can turn a vague intention into a shape that another person, or an AI system, can help us inspect. This is one reason generative AI feels so unusually powerful: it lets us work inside the medium where humans already compress thought into handles.

A word can hold a behavior in place.

Shared Symbols

At human scale, this is already how coordination works. In Sapiens, Yuval Noah Harari points to the practical force of shared stories: people can organize around symbols, agreements, and imagined structures that do not exist as ordinary physical objects. Money, laws, companies, roles, professions, and plans all depend on this capacity. They work because enough people can hold the same symbolic handle at the same time and act through it.

Language As Workbench

Generative AI changes the texture of that symbolic work. It does not merely produce text faster. It lets more people operate on language as a design material. A writer can name a recurring editorial move and ask the model to help refine it. A researcher can turn a messy method into a repeatable interview kit. A founder can describe a vague strategic instinct and gradually shape it into a reusable decision frame. The interface is not only a blank prompt box. It is a workbench for making names, aliases, schemas, and meta-schemas.

That matters because, for a long time, making executable structures belonged mostly to people who could speak the formal languages of institutions: software syntax, academic methods, legal templates, financial models, operational playbooks. Those languages are powerful, but they also create gates. If you cannot write code, you wait for someone who can. If you cannot speak the professional dialect, your insight stays informal. If you cannot convert your pattern into a recognized format, it often remains personal intuition.

The point is not that natural language replaces engineering. The point is that language can become a first layer of tool-making before engineering begins.

The new possibility is not that natural language replaces engineering. That would be both false and boring. The more interesting possibility is that language can become a first layer of tool-making before engineering begins. You can define what a process is called. You can describe when it should be invoked. You can list the values it protects, the mistakes it must avoid, the checks that tell you whether it worked. With AI in the loop, these descriptions can become active collaborators. They can be tested, revised, delegated, and reused.

Arcanum As A Live Case

Arcanum is one live experiment in this direction. In Arcanum, a name is not only decoration. A name can become an alias for a workflow. A sigil is a governed capability with a purpose, process, constraints, and validation surface. A spell composes several capabilities into a larger route. A schema gives the work a body: fields, gates, parts, dependencies, failure modes. None of this needs to be treated as mystical. It is closer to making a shared handle for a pattern that would otherwise disappear back into the day.

For example, instead of saying "help me make this article better," we can create a writing substrate. The substrate can name the target reader, the desired emotional residue, the transport type, the opening rule, the body parts, the citation policy, and the validation checks. Then the work can be developed like a small piece of software, but in the native material of language. We can draft one part, test it against the schema, notice where it fails, and let the failure teach the next version.

Aliases And Schemas

This is also where the word "alias" becomes important. An alias is a compressed invitation to a whole process. If I say "reference-first," that can mean: check the source before drafting, separate paraphrase from quotation, record what remains blocked, and only then write. If I say "reader-grounded opening," that can mean: begin with the reader's lived experience before introducing an external authority. The alias is small, but it carries an operational memory.

A schema is the next level of compression. It says: these are the parts that matter, and these are the ways they relate. A meta-schema is a reusable shape for creating schemas. For a public example, imagine a "workshop recap" meta-schema. Every recap might need the audience, the decision made, the open question, the evidence, the next action, and the tone. Once that shape exists, a person can use it across many events without reinventing the structure each time. The code is not hidden inside curly braces. It is living in a named pattern that people and machines can both work with.

Translation

The danger, of course, is private jargon. A personal symbolic system can become so personal that nobody else can enter it. That is why translation matters. A good name should not only feel meaningful to its creator. It should help someone else understand the move. A good schema should not become a shrine to complexity. It should remove friction from thought. The point is not to make language more ornate. The point is to make important patterns easier to hold, inspect, and improve.

This is the power of generative AI that I keep circling around: it gives more people a way to create their own operational language. Not just content. Not just prompts. A way to make small, living tools out of words. A designer can name a critique ritual. A teacher can name a feedback loop. A researcher can name an interview stance. A team can name the moment when strategy turns into theater and build a check against it.

If that is true, then one of the most useful questions is not "what should AI write for me?" It is: what part of my work needs a name? What pattern keeps recurring without a handle? What process do I understand only while I am doing it, but lose when I try to explain it later?

Start there. Name one workflow. Give it a purpose, a few constraints, and one way to know whether it worked. Then let the name become an object you can revise. That may be the quiet threshold where language stops being only a way to describe reality and becomes a way to build with it.
