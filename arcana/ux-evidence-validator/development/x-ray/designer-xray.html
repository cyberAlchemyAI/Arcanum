Not a UX score. A proof system.

`ux-evidence-validator` is being built to help teams inspect finished frontend interfaces with browser evidence while staying honest about what automation cannot know. It separates hard failures from design risks, screenshot review, and human-study questions.

The X-Ray View

The validator is a stack of evidence lanes. The important design move is not the Playwright script; it is deciding which claims are allowed to block, which should flag, and which need a human.

Hard gates

Things the browser can prove directly: missing names, broken keyboard paths, layout overflow, failed task flows, fatal runtime errors.

Soft flags

Risk signals with evidence, such as too many choices, weak hierarchy, hidden state changes, or a domain pattern mismatch.

Screenshot review

Captured views for visual hierarchy, salience, grouping, change visibility, and critical states that a designer should inspect.

Human study

Questions about comprehension, workload, confidence, trust, and real task success stay in a human-evidence lane.

Fixture calibration

Known-good and known-bad pages prove which checks can block, and a false-positive trap protects expert workflows.

Evidence receipt

The final output is inspectable: metadata, findings, screenshots, traces, ARIA snapshots, accessibility JSON, measurements, residue.

Where Designers Fit

Designers are not just reviewers at the end. They define what should be inspected, what counts as acceptable evidence, and which soft signals need human judgment.

Write the scenario

Name the real user task, viewports, critical regions, expected states, and the product domain. The validator should inspect what matters, not every pixel equally.

Pick review prompts

Turn design judgment into questions: Is the critical error noticeable? Is the primary action louder than nearby distractions? Does the next step need memory?

Design the fixtures

Help create known-good and known-bad mini screens: accessible, broken, clipped, dense, low-salience, domain-specific, and false-positive examples.

Set thresholds carefully

Decide when target size, overlap, clipping, density, and hierarchy findings should block, flag, or simply ask for review.

Review screenshots

Use full-page and clipped screenshots as shared evidence. A soft flag should point to a concrete region and a source card, not a vibe.

Own the residues

When the tool cannot prove comprehension or trust, decide whether the next step is expert review, prototype test, moderated study, or no action.

Use This Idea To Create Your Own

A designer can reuse the pattern for another domain, even without adopting the exact sigil. Start with claims, not tests.

1. Name the interface truth types

  1. What must be objectively true in the browser?
  2. What is a design risk but not a release blocker?
  3. What needs human evidence?

2. Make source cards

  1. One narrow claim per card.
  2. Source, evidence strength, UI scope, and proxy limit.
  3. Automation candidate: hard gate, soft flag, screenshot review, human study, or residue.

3. Design fixtures

  1. One good example.
  2. Several bad examples for deterministic failures.
  3. At least one false-positive trap for nuanced UX signals.

4. Define the evidence receipt

  1. What screenshots prove the state?
  2. What JSON should be machine-readable?
  3. What remains a human review question?

Checkout version

Hard gates: form labels, error recovery, keyboard flow, payment state, no clipped totals.

  • Soft flags: too many competing offers, hidden shipping cost, low-salience failure.
  • Human evidence: trust, confidence, comprehension of fees.
  • False-positive trap: power-user checkout with dense but grouped controls.

The designer loop

Imagine

Use Whisper to turn a vague product feeling into a clear narrative, audience, promise, and artifact direction.

Understand

Use Guide and x-ray to map the system, the workflow, the vocabulary, the hidden dependencies, and the places users can get lost.

Shape

Use refinement, distillation, and implementation layering to choose the smallest coherent tool that proves the concept without shrinking the ambition.

Build

Use task-session and experiment harness patterns to move from design artifact to fixtures, prototypes, evidence packs, and repeatable checks.

Learn

Use UX Evidence Validator, signal observation, and workflow reflection to separate what worked, what failed, and what should become reusable design knowledge.

Start with a promise

Write what the tool should help a person become capable of doing. Then use Whisper-style intent to define voice, audience, proof, and emotional residue.

Draw the invisible system

Use x-ray thinking to name actors, steps, components, dependencies, risks, and open questions before the UI becomes a collection of screens.

Choose the evidence

Decide which claims need browser proof, screenshot review, expert judgment, or user research. This prevents automation from becoming theater.

Build fixtures before rules

For every rule you want to enforce, create a good example, a bad example, and a tricky example that should not fail.

Keep residues alive

If the system cannot prove trust, comprehension, or ambition yet, keep those as named residues that can drive research instead of being forgotten.

Turn learning into infrastructure

When a review teaches you something durable, promote it through the right Arcanum owner instead of leaving it trapped in one meeting or one file.
