Friend summary

Graph memory needs ontology governance.

The chat is about adaptive retrieval: a local model evaluates requests and responses, a graph database stores weighted relationships, and the query system learns what context matters. Our ontology work is the missing governance layer: it says what kind of relation is being changed, why it is allowed to change, how confident we are, and when a claim is promoted or rejected.

The shortest version

Your friend is building a memory substrate. We are building the contract that keeps that substrate explainable.

What they are building

Embedded graph RAG

A lightweight database that can store chunks and weighted relationships close to the application, without requiring a large external platform first.

Adaptive relevance

The model receives copies of requests and responses, evaluates usefulness, and suggests which relationships should strengthen, weaken, appear, or decay.

Portable mutation layer

A bounded API or worker applies the actual graph mutation, making the system portable, auditable, and usable by smaller local models.

What our ontology work adds

Typed meaning, not just links

Our branch model separates claims into meaning, system, operational, and bridge contexts. That means the graph can know whether a relation is about a concept, a mechanism, a situated use case, or a validation bridge.

Governed state changes

Our schema separates evidence from commitment. A model can suggest that something seems useful, but promotion, contradiction, and retirement need explicit lifecycle and governance rules.

Ontology governs

Branch context, record kind, confidence, and lifecycle say what the update means.

The model can reason about which primitive applies. The worker owns mutation. The ontology records the claim, evidence, confidence, branch, and promotion boundary.

The schema states, in plain language

The schema is not just a bag of labels. Each field answers a different question about a memory object or graph relation, so the system can adapt without becoming opaque.

1. Branch context: where the claim belongs

This says what kind of thing the record is about. It prevents a database edge, a user context, and a concept definition from being treated as the same kind of truth.

meaning system operational bridge

2. Record kind: what shape the record has

This says what family of record we are looking at. A chunk of evidence, a promoted change record, and a bridge validation need different rules.

ontology_entry promotion_record evidence_input bridge_validation

3. Lifecycle status: how relied-on it is

This tracks maturity. A raw signal can influence retrieval lightly, but a promoted claim can shape stronger behavior only after evidence and governance gates.

raw catalogedEvidence reviewableSignal promotionRecordDraft candidate premise reviewed promoted contradicted retired rejected deferred

4. Claim role: what the record is doing

This is the semantic job of the claim. It keeps “this is evidence” separate from “this is a policy” or “this contradicts something”.

hypothesis observation evidence premise principle policy constraint invariant contradiction retirement other
State family Values Meaning for graph memory
Governance outcome none, policy, constitution, axiom Most graph updates are none. A small number become rules the system must follow, such as a retrieval policy or a constitutional constraint.
Bridge outcome aligned, partial, drift, insufficient, contradicted, not_applicable, unknown This says whether an edge actually connects two things well. It is where “this retrieval was useful” becomes explainable instead of just a number.
Confidence evidence, commitment, bridge_alignment, scope Evidence can be strong while commitment stays low. That is important for model-scored memory: the system can notice a pattern without trusting it too much yet.
Governance state promotion_state, next_gate, promotion_blockers, contradiction_path, circular_authority_check This is the audit layer. It says what must happen before an adaptive relation becomes a stable memory rule.

This is the deeper connection: a graph database stores the adaptive shape, but the ontology schema stores the reason the shape is allowed to change.

The design principle

Do not make the model the database owner

The model should suggest semantic moves: reinforce this edge, decay that edge, mark conflict, propose a new relation. A deterministic worker should decide whether and how the state changes.

Do not make the graph meaningless state

Every useful edge should eventually answer: what branch does this belong to, what evidence supports it, what confidence is evidence versus commitment, and what gate would promote or retire it?

Good questions to ask next

1. What are the allowed mutation primitives: reinforce, decay, contradict, trace, promote, retire?
2. What is the maximum edge-weight change per observed event?
3. What evidence must exist before a relationship can be used for retrieval?
4. What separates a useful retrieval hint from a promoted memory claim?
5. How does the system roll back a bad model evaluation?
6. Which parts must run on device, and which can be platform-side?
