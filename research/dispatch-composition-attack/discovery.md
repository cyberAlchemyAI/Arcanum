# Discovery — implementing the DISPATCH-COMPOSITION-MODEL in Arcanum

> **v0.2.0 delta (reconcile trigger for the three views):** added §7 "Where each change lands (canonical edit map)"; refined §1 "What's broken" to name canonical sources over generated copies and to record that the missing Claude hook surface is a `tools/bootstrap_arcanum.sh` generator gap (only the Codex surface is emitted). Views below reconcile against this version.

## Objective

Wire Claude-Code observability so a subagent dispatch emits L1 ledger rows through the existing writer, and extend `dispatch-spec` with a Wave band and strategy-as-typed-object. The end state is a green observed dispatch landing a `dispatch.started`+`dispatch.closed` pair in the root ledger, plus a `dispatch-spec` carrying the two structures Arcanum lacks — with the typed-DAG changes fenced behind a cross-repo decision that is not ours to make.

---

## 1. Business Context

**Why now.** The consolidated `TO-VLAD/DISPATCH-COMPOSITION-MODEL.md` is the current converged reading of subagent-dispatch governance, but its observability half is unrealized: the central ledger holds a single bootstrap record in one proof folder and zero cross-run rows (model §12.1 at `DISPATCH-COMPOSITION-MODEL.md:390-395`). Until a dispatch actually emits, the model's mandatory-emit gate (`:278-281`) is documentation, not governance, and the 32 ungoverned multi-agent folders the discovery counted stay ungoverned.

**What's broken** (each with a location; canonical source named, since the obvious copy is often generated — see §8):
- **No Claude hook surface, and it is a *generator* gap.** `.claude/settings.json` does not exist at root (Glob → none; `research.md:31,44`). The generator `tools/bootstrap_arcanum.sh:1772-1810` emits **only** the Codex surface — it copies the hook scripts into `.codex/hooks/` and writes a `.codex/hooks.json`, but never emits a `.claude/settings.json` hooks block. So nothing fires under Claude Code, and a hand-written `settings.json` would be orphaned outside the generation mechanism.
- **The hook Codex-coupling lives in the canonical source, not the copy.** `framework/observability/scripts/arcanum-hook-user-prompt-submit.sh:15-16` derives `run_id` from `.turn_id` / `session_id // "codex-hook-session"` (absent in Claude payloads → every turn collapses to one `run_dir`, identical dedupe keys); `framework/observability/scripts/arcanum-hook-stop.sh:28` reads `.last_assistant_message` (absent in Claude's `Stop` → every dispatch logs `partial`, false-positive reflection storm). The `.codex/hooks/arcanum-*.sh` are generated copies (`post-tool-use`/`stop` identical; `user-prompt-submit` an extended 208-line variant), so the patch lands in `framework/observability/scripts/` (`research.md:45-46`).
- The §12.3 envelope producer carrying authored `goal`/`angle`/`anti_bias` does not exist on disk; `register-dispatch` writes only `telemetry/agents/subagents-dispatch.yaml` and never calls `observe-invocation.sh` (`research.md:47`).
- `framework/observability/scripts/arcanum-hook-user-prompt-submit.sh:11` reads only `.codex/commands` / `.agents/skills` (26 of 46 skills); `.claude/skills` — including `dispatch-spec` itself — is invisible (`research.md:48`).
- The **canonical** dispatch-spec `formulae/dispatch-spec/SKILL.md` + its schema `formulae/dispatch-spec/dispatch.schema.json`/`.yml` + validator `formulae/dispatch-spec/scripts/validate-dispatch.py` have flat `steps[]` with no functional band above the step (Rule 1), `subagent_strategy` with no reusable `(role-set, grader)` reference (Rules 21–25), and a Rule 3 `pattern` enum conflating five categories (`research.md:64-65,80`). The `.claude/skills/dispatch-spec/SKILL.md` copy is generated from this canonical source.

**What stays the same** (scope boundary):
- **Edit canonical, never the generated copy.** All changes land in canonical sources (`formulae/…`, `framework/…`, `tools/bootstrap_arcanum.sh`); the generated surfaces (`.claude/skills/*`, `.codex/hooks/*`, `.codex/hooks.json`) are regenerated by `bootstrap_arcanum.sh` and must not be hand-edited (they carry `mutation_policy: regenerate-from-canonical-source`). See §8.
- `framework/observability/scripts/observe-invocation.sh` stays the sole ledger-writing authority — it is fed, never ported or replaced (model §12.1 at `:427-428`).
- Base rule R30, premise P-SS-9, and `OQ-mixed-dag-schema` are NOT touched here; everything that would reopen them is fenced into Phase 2b (`research.md:76-78`).
- L2 (wave) and L3 (agent) receipt rows are out of scope — they need the Craft Stage Receipt YAML and are a later increment (`research.md:38`).
- domainspec's `register-dispatch` YAML ledger and its hooks are unchanged; this is Arcanum-side wiring.

## 2. Core Concepts

- **Producer, not replacement.** A new envelope-producer Formula (stateless, schema-validate-or-reject, idempotent) emits a conformant `invocation-envelope.json` carrying authored fields and calls the existing `observe-invocation.sh`. Chosen over porting domainspec's appender because a second writer would fight the existing dedupe/index/counter owner (`research.md:33-38`; model §12.3).
- **Claude-native existence layer.** A `run_id` derived from `session_id` + a turn counter (not `turn_id`) and a completion signal read from a field actually present in Claude's `Stop` payload (not `last_assistant_message`). This is the design correction that turns "fits now" into "works now"; without it Phase 1 produces zero usable rows (`research.md:45-46,52`).
- **Wave band.** A `waves[]` grouping that wraps existing `steps[]`, each wave carrying `wave_id`/`lane`/`intent`, supplying the functional band above the step that Arcanum lacks (model §1, §8; `research.md:64`). Additive: steps keep being validated by Rules 3–7.
- **Strategy as a typed object.** A `strategy_ref` on `subagent_strategy` pointing to a reusable `(role-set, grader)` definition (`research`, anchored to domainspec's `research-constitution.md`); absent `strategy_ref`, nothing breaks (`research.md:65`).
- **The Phase 2a / 2b partition.** The single partition criterion is *does the change need a typed-DAG / reopen R30*. Everything additive (Wave grouping, `strategy_ref`, verdict vocab, `pattern` cleanup) is 2a; everything requiring typed `consumes`/`reviews`/`reopens` edges is 2b (`research.md:68-78`).
- **Ratify-the-draft, not invent-the-DAG.** The typed-DAG already exists, unratified, in domainspec's own `subagents-strategy-constitution-proposal.md` v0.5.2 (`status: draft`); so the cross-repo call is promotion, not invention (`research.md:86`). *(Relayed from the sibling repo; not re-verified in this tree — see Open Questions.)*

## 3. Phase 1 — observability wiring (the ready increment)

The smallest shippable increment makes one dispatch emit an L1 row pair traceable to `subagents-dispatch.yaml`. Three design elements plus two corrections:

- **Hook surface** — a `.claude/settings.json` hooks block mirroring the three Codex events (`UserPromptSubmit`/`PostToolUse`/`Stop`). The `PostToolUse` matcher is `Bash|Edit|Write` (Claude) where Codex uses `apply_patch`.
- **Scaffold** — `signals/` + `reflection-state.json` materialized via the `observability-setup` Formula (canonical) rather than a bare `mkdir+touch` (which leaves `reflection-state.json` unmanaged). `observe-invocation.sh:58-63` self-creates the directory, so the scaffold is correctness-for-counters, not a hard blocker.
- **Envelope producer** — emits `invocation-envelope.json` (template `framework/observability/templates/invocation-envelope.json:1-33`) with `goal`/`angle`/`anti_bias`/`exit_reason` as typed extensions; `started` → `status:"partial"`, `closed` → `"completed"` with dedupe key `dispatch-<id>:close`.
- **Correction A (run_id)** — replace the `turn_id` derivation; a Codex-coupled field cannot identify a Claude turn.
- **Correction B (completion)** — derive completion from a present Claude payload field; otherwise every row is `partial`.

Reuse map: `observe-invocation.sh`, `arcanum-post-tool-use.sh`, and `arcanum-stop.sh` are reusable once the hook surface and the two corrections land; `arcanum-user-prompt-submit.sh` needs extension (it exits `{}` for any non-`/command`/`$skill` prompt).

## 4. Phase 2a — dispatch-spec schema (additive, no cross-repo decision)

- **Wave band attach point** — `waves[]` added to Rule 1's structure as an optional grouping; `wave_id` FK added to the Rules 23–25 lifecycle entries for L2 logging, without changing lifecycle validation logic.
- **`strategy_ref`** — added to the existing `subagent_strategy` block; the referenced definition lives at `formulae/dispatch-spec/strategies/<name>.yml` (colocated with the spec, reusable across dispatches) rather than inline per dispatch.
- **Verdict vocabulary** — `pass | flag | block` carried on waves (model §6).

## 5. Cleanup — mode-conflation in the `pattern` enum

Minimum safe slice when Rule 3's enum is touched: drop the four function-words (`distill`/`synthesis`/`validation`/`decision`) and require them in `subagent_strategy.roles[]` (tightening Rule 21); move the two overlays (`xray`/`toy_game`) to the technique-overlay catalog (Rule 12). `route`/`sequential`/`handoff` collapse into the Connection layer and are deferred to Phase 2b because they are entangled with the typed-edge wiring (`research.md:80`).

## 6. Open Questions

Each carries a recommendation.

- **OQ-1 — the Vlad gate (blocks Phase 2b only).** Ratify v0.5.2-proposal · single-canonical-spec collapse · P-SS-9 discharge · `loop_cap` default (`research.md:89`; `TO-VLAD8.md:265-276`). *Recommendation:* do not start Phase 2b until all four clear; proceed with Phase 1 and Phase 2a in parallel, which none of them gate.
- **OQ-2 — Claude completion signal.** Which `Stop` payload field reliably signals completion under Claude Code, replacing `last_assistant_message`? *Recommendation:* inspect a live Claude `Stop` payload and prefer `transcript_path`-derived state; treat it as the gating proof for Phase 1 "done".
- **OQ-3 — Claude-native run_id.** Is `session_id` + turn-counter stable and monotonic across a session? *Recommendation:* confirm empirically with a two-turn session before building the producer on top of it.
- **OQ-4 — skill-detection coverage.** Should the L1 producer depend on skill detection at all, given `arcanum-user-prompt-submit.sh:12` sees only 26 of 46 skills? *Recommendation:* decouple the producer from skill detection — drive it from the dispatch envelope, not the prompt route.
- **OQ-5 — cross-repo verification.** The v0.5.2 and R30-verbatim claims were read in the sibling domainspec repo, not re-verifiable in this tree. *Recommendation:* confirm against the live domainspec tree before any ratify decision (this is exactly why OQ-1 is Vlad-reserved).
