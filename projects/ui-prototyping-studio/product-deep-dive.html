UI Prototyping Studio

A guided way to try UI ideas with Claude Code: make a few HTML options, look at them in a browser, click the parts you want changed, preview the result, and keep a clean history of what changed.

What is it? A local studio for making, comparing, annotating, and revising HTML UI prototypes.
Who drives it? You and Claude Code share the same `studio` CLI, while the browser preview shows the actual UI.
What comes out? A chosen HTML revision, an append-only history, and an exportable handoff bundle.

Examples

Three ways someone would try the studio.

These examples are intentionally plain. They show the tool from the user's side before naming the internals.

Example 1

Create a sign-up card

Prompt: "Make a sign-up card for a calm analytics app."

What happens: Claude Code creates HTML variants, you choose one in preview, then you comment on the CTA or helper text.

Useful command shape: studio variants register <sid> --from ./variants

Example 2

Refine a login screen

Prompt: "Keep this login screen trustworthy, but make the password-reset path easier to notice."

What happens: you comment on a specific component, the studio turns that comment into a change task, and the candidate must stay inside that scope.

Useful command shape: studio apply <sid> <batch> --candidate-from candidate.html

Example 3

Run a reversible AUTO pass

Prompt: "Try one exploit pass that makes the current CTA clearer."

What happens: the studio can score proposed candidates, keep the best admitted one, and still let you revert because history is append-only.

Useful command shape: studio cycle <sid> exploit --objective "clearer CTA" --candidate continue.html:0.9

How It Was Made

It is a small local backend with a CLI, a browser preview, and a strict core.

Once the workflow is clear, the implementation is easier to understand: adapters talk inward to the core; generated HTML comes from outside.

Inside Boundary

Rules, state, storage, preview

`domain/` defines the session state and invariants. `application/` owns use cases and gates. `infrastructure/` stores session and artifact content. The CLI and preview are adapters.

Outside Boundary

Generation engine and host operator

Claude Code creates variants and proposed candidates. A human or host app drives the CLI. Future MCP or SDK adapters can plug in behind the same operations.

Lifecycle

The session state machine is the product's spine.

Reader outcomes: after this layer, you should understand where the user can intervene and where the core refuses invalid movement.

2. PromptCapturedThe user's UI objective is recorded.
3. VariantsReadyHTML variants enter through the generator seam.
4. BaselineReadyA baseline is selected or committed.
5. CommentsCapturedComponent-level intent becomes durable input.
6. MutationDraftedComments deterministically fold into tasks.
7. MutationApprovedIntent is approved before any candidate applies.
8. RevisionAppliedCandidate is staged; head has not advanced.
9. RevisionRecordedAccepted candidate becomes append-only history.
10. SessionCompletedExport is terminal and explicitly confirmed.

Control Model

The studio checks the proposed change before it becomes the saved version.

Claude Code can be creative. The studio's job is to ask a simpler question: did this candidate stay inside the change the user asked for?

Gate 1

Approve the plan

The studio first shows the change tasks it inferred from your comments. This is the "yes, try that" moment.

Check

Keep the change inside the target

The candidate is checked against the component ids from your comments. Unexpected edits are rejected instead of silently accepted.

Gate 2

Accept what you saw

The staged version is shown before it becomes the new head. Accept keeps it; discard leaves the previous version in place.

Part of the tool Plain meaning Why a user cares
Small variant set The studio asks for only a few options at a time. You compare real alternatives instead of scrolling through endless generated noise.
Baseline choice You pick the version to continue from. Later comments and revisions have a clear source.
Scope check The studio compares the candidate to the component you asked to change. A button-label edit should not secretly redesign the whole card.
Append-only history Each accepted change adds a record instead of erasing the past. You can inspect or revert without losing the trail.
Export confirmation Handoff is the final explicit step. The tool does not accidentally send unfinished work downstream.

Careful Parts

What a new user should not misunderstand.

The studio is useful because it makes changes visible. That is different from proving the design is good, preferred, or trusted.

Misunderstanding Better reading Why it matters Where the tool is going
"The browser test proves users trust it." The browser test proves what happened on screen. Trust and preference still need human evidence. Human-study and UX evidence work.
"The scope checker understands every UI change." It checks stable component ids and known structure. Large structural changes need stronger identity logic. Component identity and registry work.
"AUTO mode means unattended production design." AUTO is a reversible local cycle. It is for exploration, not final judgment. Better scoring and calibration.
"All future layers are already live." The current tool is the local workflow floor. Identity, fitness, and trust layers should stay clearly marked. Roadmap after the workflow is solid.
