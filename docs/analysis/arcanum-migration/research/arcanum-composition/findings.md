## Conclusions

1. Arcanum’s current composition is plural and authority-bound. It is not one
   linear pipeline or one shared state machine.
2. Communication is operationally visible through artifacts, dispatch bindings,
   receipts, approvals and owner-mediated state synchronization.
3. Contracts are materially ahead of some current integrations. The strongest
   bounded cross-owner execution witness is Task Session → Invoke Refresh;
   Goal’s current packaged behavior remains largely read-only and fixture-backed.
4. Craft-backed durability is a separate owner action. A native result, decision
   record, staged delta or route string does not itself mutate the ledger.
5. Evidence authority is concern-specific. Intended responsibility, implemented
   binding and observed execution must remain separate whenever sources disagree.

## Implications

For the current analysis, describe relations one by one with their caller,
transferred object, owner, gate and evidence status. Treat Invoke preparation as
a conditional governed path into Task Session, not a universal prerequisite.
Describe Goal as an explicit composition contract with partial runtime witnesses,
not as proof that the full autonomous loop is deployed. Present the missing
generic Craft write-back adapter/actor, Goal runtime seams, Task Session owner
hooks and source-precedence ambiguity as research residue requiring product-owner
judgment before any improvement is selected.

## Dissent and contrary evidence

- The runtime explorer classified RQ-3 through RQ-9 as answered within its
  relation matrix. This synthesis retains `unresolved` for RQ-4, RQ-7 and RQ-9
  because the binding template requires the *whole* RQ to be resolved: the
  generic Craft write-back actor/adapter and same-concern authority precedence
  remain unspecified.
- Task Session’s contract admits narrowly automatic
  `invoke:refresh:apply-approved` closeout, but the main deterministic runner says
  owner hooks and continuation are not implemented; one historical chain proves
  the bounded protocol, not current universal automation.
- Goal’s contract describes an autonomous Craft-backed loop, while its current
  runtime consumes caller-provided nodes, creates synthetic receipts and never
  writes Craft state.
- The inspected historical Craft mutation is attributed to `local-fallback`, so
  it cannot be promoted into evidence of a packaged Craft apply runner.
- Generated skill packages, canonical contracts and the Spell Registry disagree
  in versions and coverage; no conflict is silently resolved in these findings.

## Limitations and evidence boundary

Research was repository-only. No web sources or live end-to-end capability run
were used. The explorers inspected current contracts, schemas, deterministic
source, stored fixtures, receipts and bounded historical runs. Stored observations
prove only their named fixtures/runs; source code proves an implemented path or
omission but not successful execution; contracts prove documented authority but
not runtime binding. Negative findings are limited to the named current packages,
registry/schema surfaces and relations inspected. Private consumer adapters,
unrecorded operations and unrelated Arcanum capabilities are outside scope.

## One-line answer to the research goal

Arcanum currently supports multiple authority-bound, artifact- and receipt-mediated compositions with uneven implementation and bounded witnesses, while generic Craft write-back, full Goal orchestration, same-concern source precedence and improvement prioritization remain unresolved.
