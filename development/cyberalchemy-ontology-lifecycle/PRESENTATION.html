Why This Exists

Agentic systems produce a lot of traces: tool calls, validations, route outcomes, failures, retries, and reflection notes. Some are useful. Some are noise. None of them should become authority just because they were observed.

Problem

Memory is too soft

Raw memory helps agents recall, but it does not decide what should govern future behavior.

Problem

Telemetry is not truth

A trace proves that something happened. It does not prove what that event means for the ontology.

Need

Knowledge needs gates

Claims need evidence, confidence, scope, ownership, and a path for contradiction before agents rely on them.

The Core Model

The selected architecture centers on one governance object: PromotionRecord. It is the bridge between evidence and ontology state.

Candidate knowledge

Can guide review. It stays visibly uncertain, scoped, and reviewable.

Promoted knowledge

Can guide operation only after evidence, confidence, owner, scope, and contradiction gates pass.

Four Ontology Areas

CyberAlchemy separates knowledge by authority boundary. Business, System, and Bridge are the stable baseline. Operational Ontology remains a candidate extension until accepted.

Stable

Business Ontology

  • Domain language
  • Actors and value
  • Policies and business rules
  • Business-facing invariants
Stable

System Ontology

  • Codebase facts
  • Services, APIs, data flows
  • Tests and infrastructure
  • Runtime behavior
Stable

Bridge Ontology

  • Traceability
  • Drift and contradiction
  • Evidence links
  • Validation relationships
Candidate

Operational Ontology

  • Agent routes
  • Capability behavior
  • Workflow lessons
  • Route policies and context patterns

Promotion Lifecycle

The lifecycle gives contributors a safe path from discovery to use. The important move is that every meaningful knowledge change passes through a PromotionRecord.

L0-L2

Evidence before meaning

Raw observations become source selectors, inventory evidence, reviewable signals, or lifecycle envelopes.

Draft

PromotionRecord draft

A single claim receives source inputs, provenance, branch target, confidence fields, owner, and contradiction path.

Review

Evidence and confidence review

Evidence confidence asks whether the claim is supported. Commitment confidence asks whether agents should rely on it now.

Outcome

Promote, defer, reject, contradict, or retire

The model keeps uncertainty and contradiction visible instead of overwriting history.

Feedback

Operational use creates new evidence

Observability feedback can start a new PromotionRecord, maintenance route, or contradiction review.

Contributor Guardrails

These rules keep the ontology useful without making it brittle. They are the habits new contributors should internalize first.

Do not

Promote from telemetry directly

A ReviewableSignal can start or support review. It cannot create promoted knowledge by itself.

Do not

Hide candidate status

If a claim is candidate, deferred, contradicted, or uncertain, its status must stay visible.

Always

Split confidence

Evidence confidence and commitment confidence answer different questions and must not collapse into one score.

Always

Preserve contradiction paths

Good ontology work does not erase failed claims. It records why they were rejected, deferred, or retired.

How To Contribute

The reviewed package recommends a review-only first slice before canonical adoption. That gives contributors a concrete, low-risk way to prove the model.

1

Read the first slice

Start with FIRST-WORKING-SLICE.md and its validation checklist.

2

Create one fixture

Represent one operational lesson as a review-only PromotionRecord.

3

Validate fields

Check claim, source inputs, confidence split, owner, branch target, use scope, and contradiction path.

4

Run bridge review

Decide whether evidence is aligned, partial, drifted, insufficient, or contradicted.

5

Keep it non-canonical

Do not mutate ontology, runtime, skill, sigil, spell, or observability files until acceptance.
