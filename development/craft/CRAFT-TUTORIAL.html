Durable state for agentic work

Craft keeps project state from disappearing between sessions.

When a project spans multiple AI conversations, the fragile part is not only code. It is memory: decisions, blockers, evidence, gaps, and what should happen next. Craft stores that state in files the project can carry with it.

ledger.ymlThe machine-readable source of truth for Craft state.
CRAFT.mdThe human-readable view derived from the ledger.
recompositionThe proof that child work changed the parent context.

The Problem

AI-assisted projects lose state easily. A chat gets compacted. A task spans more than one session. A decision is made in a review note but never appears in the next plan. A blocker gets called resolved because everyone wants to keep moving.

The Mental Model

Think of Craft as a map of unfinished work. Each row answers one simple question about where work lives, what exists, what is blocked, what was decided, what is missing, and what happens next.

context

Where the work lives

A context can be the whole project or a child task with its own evidence and blockers.

artifact

What exists

An artifact points to a file, handoff, receipt, validation, source, or human view.

blocker

Why motion stops

A blocker stays visible until evidence or an explicit waiver closes it.

decision

What authority chose

A decision records the question, selection, rationale, impact, and evidence.

gap

What remains weak

A gap preserves missing, deferred, or fragile work without pretending it is a blocker.

recomposition

How child work returns

A child context is not done until the parent records what changed upstream.

The Files

ledger.yml owns state. CRAFT.md helps people read it. If they disagree, the ledger wins.

.craft/
  ledger.yml        # source of truth
  index.json        # optional rebuildable lookup surface
  artifacts/        # receipts, handoffs, evidence, exports
CRAFT.md            # human-readable view derived from the ledger

Guide Lens

Use the Guide package pattern when teaching or reading Craft: frame the target, inspect the existing context, explain in order, check understanding, then record what should be remembered.

The Protocol

Use Craft when the project state itself needs memory. Do not use it for every tiny edit.

1. ResolveFind the right Craft space before touching a ledger.
2. ReadUse ledger.yml as source of truth.
3. RecordAdd rows for real changes, not vague impressions.
4. BlockKeep blockers visible until evidence closes them.
5. DecideRecord question, selection, rationale, impact, evidence.
6. RecomposeReturn child context results to the parent.
7. ExportRefresh CRAFT.md as a view.

A Small Example

A product launch has an API boundary question and missing pilot evidence. The API review can pass while the product launch root stays flagged. That is the point.

What Craft Records

  • CTX-PRODUCT-LAUNCH-ROOT - the launch readiness context.
  • CTX-PRODUCT-LAUNCH-API-REVIEW - a child review context.
  • DEC-API-BOUNDARY-001 - the selected API boundary.
  • BLK-PILOT-EVIDENCE-001 - the active readiness blocker.
  • GAP-SEED-DATA-001 - fixture data still needs a pilot check.

Blockers, Lanes, and Roles

A good blocker says why motion stopped, who owns the next responsibility, what local role may handle it, and what evidence would prove it closed.

item_id: BLK-PILOT-EVIDENCE-001
kind: blocker
base_type: evidence_blocker
primary_lane: validator
secondary_lanes:
  - product
status: active
refinement_status: refined
default_role: evidence_reviewer
allowed_roles:
  - evidence_reviewer
  - validator
delegation_route: task-session
requires_human: false
role_confidence: candidate
closure_condition: A pilot run produces a receipt.
evidence: ART-PILOT-EVIDENCE-PLAN
decision_ref: none

How to Read It

Type explains the cause. Lane names the responsibility. Role names the local handler. Route suggests a workflow. Closure says what proof is required.

lane

Responsibility type

validator says validation responsibility owns the next move.

role

Local handler

evidence_reviewer is a project-local role, not global Craft vocabulary.

route

Suggested workflow

task-session may produce evidence, but route shape is not execution proof.

closure

Evidence required

A raw blocker cannot close directly. It must be refined, resolved with evidence, or explicitly waived.

Common Mistakes

Craft is small, but it is picky about authority and evidence.

Closing a raw blocker directly

Refine it first. Attach evidence or a waiver decision.

Treating dispatch as execution proof

Dispatch validation proves route shape, not that the work happened.

Updating only CRAFT.md

The human view can drift. Update ledger.yml first.

Leaving child work unrecomposed

The parent never learns what changed unless recomposition is recorded.

The First Run

Start with one root, one blocker, one child context, one decision, one gap, and one recomposition. If that feels too heavy, Craft is probably too heavy for the task.

RootCreate the project context.
BlockerAdd the thing that stops safe motion.
ChildOpen a context to refine it.
DecisionClose or defer a real choice.
ReturnRecompose into the parent.

Teach-Back Check

Before operating a Craft ledger, answer these in your own words.

  1. What is the source of truth: ledger.yml or CRAFT.md?
  2. What must happen before a raw blocker can close?
  3. Why can a child context pass while the parent stays flagged?
  4. What evidence proves the next move is allowed?
